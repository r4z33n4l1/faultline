# Faultline and the Agent Baseline boundaries

Access date: 2026-11-01.

Source: [The Secure Software Factory: A Reference Architecture](https://agentbaseline.org/reference-architecture) (Agent Baseline, open for comment, 13 October 2026). The page describes a software factory that turns a prompt, ticket, or specification into tested code. It separates what an agent decides from what it may do: the agent proposes, policy authorizes, and infrastructure enforces. Four boundaries enforce that from outside the agent's own decisions. The page's three autonomy levels (a person, a workflow, or an agent chooses the next step) keep the same four boundaries. Faultline does not model those levels and does not take over supervision as autonomy increases.

The four boundaries, in the page's words:

| Boundary            | What it limits                            |
| ------------------- | ----------------------------------------- |
| Sandbox             | Where the agent's code runs               |
| Network             | Which systems and operations it can reach |
| Supply chain        | Which components and sources it can use   |
| Identity and access | Who the agent acts for and what it may do |

The page's incident example is an agent allowed to read one service's logs for the last hour. If it asks for another service's logs, a proxy blocks the request until a new authorization decision grants them. Faultline does not implement that proxy, or any other enforcement point.

## How to read the map

Faultline scans application source and writes unvalidated candidates. It does not sandbox a process, proxy a connection, admit a dependency, or decide who an agent acts for. A row below is **partial** when a check looks at source that is related to a boundary and stops short of enforcing it. A row is **not covered** when Faultline has no check for that control, or when the check that exists is about something else. **No row is covered.**

Hunters and the coverage ledger are file or route crossed with `authz_idor`, `injection`, `secrets`, and `ssrf`. Recon signals are inventory fields on the way to `architecture.md`. The disproof validator is planned and is not in this tree. `findings.json` stays empty until that validator exists. `faultline validate` only checks that a findings file matches the schema.

With no model provider, `architecture.md` is an inventory note. It says trust boundaries were not summarized.

## Validator

| Check                      | Boundary         | Result      | What it is                                                                                                                                                                                        |
| -------------------------- | ---------------- | ----------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `faultline validate`       | None of the four | Not covered | Schema check of a findings file. It does not disprove a candidate and does not authorize an action.                                                                                               |
| Planned disproof validator | None of the four | Not covered | Not in this tree. It is being built separately. When it exists, it is a claim check before something is called a finding. It still would not enforce sandbox, network, supply chain, or identity. |

Configuring `--provider` makes this CLI open its own connection to the provider in `FAULTLINE_BASE_URL` or the provider default. That is Faultline's network use. It is not a network-boundary control, and the tables above do not count it as one.

## Gaps

Nothing here enforces a boundary. The factory controls that are absent:

- **Sandbox.** No OS sandbox, no runtime confinement, no split between where generated code runs and the credentials of the person or agent that invoked it. Command and code sinks are source patterns in the program being scanned.
- **Network.** No egress proxy and no per-operation allow. The log-reader example on the Agent Baseline page, where a proxy blocks a second service until a new grant, is not something Faultline does. SSRF coverage is same-function source text. DNS rebinding, redirect chains across functions, and client instances such as `axios.create` are not checked.
- **Supply chain.** No dependency allowlist, no lockfile verification, no signature or provenance check. Dependency directories are skipped on purpose, so a vulnerable or substituted package is invisible to the scan.
- **Identity and access.** No agent identity, no on-behalf-of user, no just-in-time grant, no external policy decision. Authz/IDOR is the application's object check, and only when the hunter can see it in the handler. Secrets are redacted fingerprints of literals, not a credential broker.
- **Autonomy levels.** The four boundaries are the same at each level on the Agent Baseline page. Faultline does not record which level a run is, and it does not add supervision as the agent chooses more of the next step.

## Deferred: `boundary` on the coverage ledger

A `boundary` field on `coverage.json` was considered and left out.

The ledger schema is version `"1"`. Each unit is a strict object: one file or route, one bug class, a status, and a reason. Hunters only replace status and reason. Writing the field in `buildCoverage` would be a small code change, and `schema:check` would regenerate `schema/coverage.schema.json`.

The field would still be the wrong contract. `secrets` is both identity and supply chain. Command injection is only adjacent to sandbox, while SQL injection is not one of the four boundaries. `authz_idor` is not the agent's identity. Recon signals and the planned validator are not ledger rows, so a field on the unit would miss most of this map and would read as stronger coverage than the scan has. The map stays in this document until a unit can name more than one boundary without collapsing the gaps above.
